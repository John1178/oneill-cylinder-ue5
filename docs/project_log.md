## Working rules (for Claude)

### 1. Evidence, not inference

**Do not reason from my own logic and present it as fact.** Claims about tools, engines,
licences, job markets, hiring bars, or best practice must be backed by a source — official
documentation, a real job posting, a vendor page — not reasoning that sounds plausible.

**Search BEFORE answering, not after being challenged.** If the answer is being constructed
from what seems sensible rather than from something read, that is the trigger to search.

### 2. Search is mandatory for these

- Engine/tool feature claims — what a node is called, what a version supports, whether an API exists
- Licence terms, pricing, file-format compatibility
- Job market claims — what employers want, seniority bars, salary, which skills matter
- "Best practice" or "how studios do it"
- Anything where being wrong costs money or days of work

### 3. Read the source, don't skim the snippet

Search result summaries are often wrong or incomplete. Where the detail matters, fetch and read
the actual page. If a page can't be reached (403, JS-rendered, paywalled), **say so** — do not
fill the gap with a guess and present it at the same confidence.

### 4. Label confidence honestly

Three different statements, never blurred together:

- "I checked X, here is the source" — verified
- "I believe X but haven't confirmed" — unverified, flagged
- "I don't know" — say it

Citing sources at the end of a response is required when the answer came from search.

### 5. Verify against the live project, not memory

Query the editor, read the file, check the repo. The MCP API and the user's screen have
disagreed more than once in this project — when they do, **the user's screen wins** and the
API is treated as unreliable until proven otherwise.

Never claim something exists, was created, or was fixed without checking it.

### 6. Why these rules exist

Real errors from this project, all caused by reasoning instead of checking:

| Error | Cost |
|---|---|
| Wrong material node names, twice, from memory | Multiple wasted turns hunting for nodes that weren't called that |
| Module list called a blocker when the data-driven design made it not | Nearly delayed Week 3 for no reason |
| Material system called portfolio-ready before searching what impresses | Would have led with a weak piece |
| `FBX_SCALE_ALL` export setting | Entire station imported 100× too small |
| "Houdini Indie will fix your `.hdanc`" | Would have been a wasted purchase — Indie has its own incompatible format |
| 62 modules generated by filling a spec without asking if the spec fit | Weeks of unnecessary modelling scope |

### 7. Division of work

Claude does: data wrangling, file conversion, boilerplate, one-off generator scripts,
verification queries, research.

The user writes: **the manifest tool** — schema, validator, UI, UE integration. Every line.
That code is the portfolio artifact and has to be defensible in an interview. AI-written code
the user can't walk through is worse than no code at all.

## Major decisions

### Station scale — rescaled 4.5×
Was 444 m diameter (≈2.0 RPM for 1g, at the Coriolis comfort limit).
Now **1,998 m diameter × 13,378 m long, 0.95 RPM, 63 s per rotation.**
Real O'Neill Island Three is 6.4–8 km × 32 km, so this is ~⅓ scale — deliberately, since a
larger habitat needs more content than 10 weeks allows. Verified against a 1.8 m human reference.

### Day/night mechanism — shutter, not mirrors
Wings rotate **closed** to block sunlight (night), **open** to let it through (day). The wing's
inner face carries a fake starfield. This departs from the real O'Neill proposal (hinged mirrors
reflecting light in) because the scope doc doesn't require simulated mirrors, Lumen doesn't
transport light through translucent glass reliably anyway, and a shutter is a genuine animated
mechanism rather than a static reflection concept. See `design_day_night.md`.

### Schedule cut from 12 weeks to 10
Merged Weeks 3+4 (Python tool written UE-aware from the start, skipping the port), cut Belt C
(scope doc only requires one hero belt), merged Weeks 9+10 (one optimization pass, not two).
Polish and delivery weeks were deliberately **not** cut — that's where the portfolio is made.

### Reordered to PCG + Python + Gaea first
The material system is competent but not a portfolio headline — MPC day/night is a documented
standard technique. The differentiating work is the procedural pipeline. Those pieces are also
individually showable, so applications can start before the project finishes.

### Module list — reworked three times
- v1: 62 modules (filled the art guide's category ranges to midpoints — wrong, that describes a
  full production kit, not a solo portfolio piece)
- v2: 30 (cut on three rules: structurally necessary / high reuse / serves the hero belt)
- v3: 37 (added Buildings and expanded Vegetation — both named explicitly in the JDs)
- v4: restructured for PCG DataTable import — see below

### Content sourcing — model 13, source 24
A PCG TA builds the system that places assets; artists author them. Sourcing most content is
production-accurate, not a shortcut. You model the 13 simplest tiling pieces (structural,
habitat surface) where modular discipline actually shows.
Megascans for vegetation, marketplace for props/buildings, **one self-scanned asset** for the
照扫 evidence JD1 asks for.

### Data path — Epic's documented route
```
module_list.xlsx -> CSV -> UE DataTable -> PCG graph -> Attribute Set
                 -> Mesh Selector by Attribute -> spawn
```
Chosen over a custom JSON+Python runtime path because it's what Epic and SideFX both do.

### What lives where — corrected mid-conversation
| Data | Where |
|---|---|
| Module catalogue (37 rows × 6 fields, asset paths, weights) | DataTable, authored via the Python tool |
| Layout tuning (road spacing, density, seed) | **PCG parameters, native** — not the manifest |
| Layout algorithm (subdivide, road network, lot allocation) | **PCG graph** |

Initially proposed putting road/block parameters in the manifest. That was wrong — PCG exposes
scalars well and they need live iteration. The manifest's job is bulk reference data and
validation, nothing more.

### City layout — Epic's CitySample is the reference

Epic ships **CitySample PCG**: 18 interdependent PCG graphs that recreate the City Sample using
*"exclusively internal Unreal Engine systems"* — the original was built in Houdini, this version
is not, which is the proof Houdini isn't required for city layout.

The documented sequence:

| Graph | Produces |
|---|---|
| `PCG_3_1_1_Districts` | Consumes boundary + arterial routes → districts, sub-districts, city blocks, first road network |
| `PCG_3_1_2_Roads` | Arteries, collectors, local streets. Solves intersections, applies shape grammar, projects onto terrain |
| `PCG_3_1_4_Lots` | Consumes city shape + road footprint → building footprints and lots |

Then `Assign City Sample Building` extrudes footprint splines to height and applies shape grammar
across 23+ architectural styles.

**Plan: adapt this, don't reinvent it.** The differentiator is not "I built a procedural city" —
Epic already did. It is that CitySample assumes flat ground (world +Z up, straight roads,
heightmap projection) and a cylinder interior breaks every one of those assumptions.

**The interview test for whether this is genuinely ours:** can I name something that broke when
moving to a cylinder, and how it was fixed? If every problem was already solved in the source
material, it is a tutorial follow-along.

### Streets — tiles, not spline-deformed meshes

**Researched because the two approaches were unresolved.** Finding: **PCG cannot deform meshes
along splines.** From the Epic forum discussion — *"PCG is designed for mesh placement rather
than mesh generation"*; *"you are looking for actual mesh generation, not mesh placement."*

Specifically:
- Static mesh instances cannot conform to curved splines without individual deformation
- Landscape Splines are **editor-only** — impractical at runtime, and they deform terrain, which
  this project does not have
- Continuous curved roads require Procedural Mesh Component, built triangle-by-triangle

**But splines still define the path.** `PCGSplineSamplerParams` samples *"along the spline at a
fixed distance interval"* — `distance_increment` sets spacing, `distance_attribute` carries
distance along the spline, and it produces **oriented** points that already face along the curve.

So the workflow is:

```
spline (road path)
  -> PCG Spline Sampler (oriented points every N metres)
  -> align each point to the cylinder surface normal   <- the hard problem
  -> Static Mesh Spawner (street tile per point)
```

**Decision: tiled streets.** Reasons — it is what PCG actually does, the module list already
assumes it (`Ground_Paved_Street`, `Pathway_Straight`), and surface-normal alignment then solves
streets and buildings with one mechanism instead of two.

Known limitation: straight tiles on a curve gap or overlap at the joins. The cylinder's own
curvature is negligible at this scale (a 10 m tile on a 1,000 m radius deviates by a fraction of
a millimetre); tight street corners inside the belt are where it would show. Mitigation is
shorter tiles or a corner piece — `DeckPlate_Corner` already exists for this.
**Not yet verified how visible the seam is at project scale — test in Week 4.**

Spline-mesh roads remain a possible upgrade, but honestly labelled: it would be a Blueprint /
Procedural Mesh system alongside PCG, not a PCG feature.

### Houdini — parked, and the licence path is closed
Existing procedural pylon was built in **Apprentice** (`.hdanc`). Houdini Engine for Unreal
cannot read that format. Indie has its own incompatible format (`.hdalc`) — buying Indie would
**not** fix it. SideFX's conversion offer requires a full perpetual commercial licence.
So: keep the pylon as a Houdini-only portfolio piece, or rebuild it later if Houdini proves
necessary. Epic's CitySample proves the city pipeline runs without Houdini.

### Dim sum game — parked
1–4 player local multiplayer, lost files from an internship. Grey-box rebuild is 3–5 days but
demonstrates gameplay/design, not TA. Better return: a written design/postmortem page with the
existing screenshot. Revisit only if the job search says gameplay roles are the realistic path.

### Toon/NPR — parked
UE 5.8 shipped a native Substrate toon shader; 5.7 has no native support. Would be a second
rendering pipeline on a fixed runway. Post-project piece if the market calls for it.

## Traps hit — worth not repeating

**FBX export scale.** `apply_scale_options='FBX_SCALE_ALL'` imports 100× too small. Use
`FBX_SCALE_NONE` and let UE do the metres→centimetres conversion.

**Negative scale flips normals.** Negative on all three axes = negative determinant = winding
flips in world space even when local mesh normals are correct. Bake the scale, then recalculate
normals outward.

**Degenerate UVs break tangents.** Meshes had UV maps with zero-area faces → "nearly zero
bi-normals" warnings. Smart UV Project cleared it. Real unwrapping is the Week 6 texture pass.

**Objects outside the view layer.** The endcaps belonged to no collection — invisible, unselectable,
and silently absent from exports. `users_collection: []` is the tell.

**Editor doesn't refresh on scripted changes.** Assets modified via Python don't update in an
already-open editor tab. Close and reopen before assuming something failed.

**MCP socket timeout ≠ failure.** A 55-mesh import legitimately exceeds the 30 s timeout.
Verify the assets before assuming it broke.

## The honest assessment

The Excel→DataTable→PCG pipeline is **competent but not impressive** — it's Epic's documented
path, and an experienced TA reads it as baseline rather than distinguishing.

**The differentiator is the curved surface.** CitySample assumes flat ground: "up" is world +Z,
roads are straight in world space, terrain projects via heightmap. A cylinder interior breaks
every one of those. Solving it — and documenting what broke and why — is the portfolio piece.

Framing matters: *"I built a procedural city in UE5"* reads as a tutorial follow-along.
*"I adapted Epic's district→road→lot pipeline to a rotating cylinder where surface normal varies
per point and roads wrap onto themselves"* is a technical breakdown.

**Spend the remaining weeks where the difficulty is.** Polishing the Excel exporter while the
curved-surface alignment is unsolved would be the wrong trade.
